# Eventernote 出勤率分析工具 — 需求与方案

## 1. 项目目标

开发一个可用于分析 Eventernote 公开数据的小工具，用于计算：

- 某个 Eventernote 用户（如 `Tokuzawa353567`）
- 对某位特定艺人（如铃木爱奈）
- 在某个自然年（例如 2025）
- 的活动出勤率

核心公式：

- 出勤率 = 该用户在该自然年中与该艺人相关的已出席活动数 / 该艺人在该自然年中的全部活动数

## 2. 业务场景

该工具适用于低频使用场景：

- 单人/小团体使用
- 每年偶尔查看几次
- 不需要实时更新
- 不需要大量用户同时访问
- 不需要数据库、复杂后台或域名

目标用户的访问方式：

- 在 GitHub 上手动触发一次分析
- 处理一个 `用户 ID + 艺人名称 + 自然年` 的单次分析任务
- 系统内部自动解析艺人名称，并在必要时解析对应的艺人页面或艺人 ID
- 查看静态网页输出结果

## 3. 需求概述

### 3.1 功能需求

1. 输入参数：
   - Eventernote 用户 ID
   - 艺人名称（例如 `鈴木愛奈`）
   - 统计年份（自然年）
   - 可选：艺人页面链接或已知艺人 URL（用于辅助解析）

2. 获取数据：
   - 抓取用户公开活动列表
   - 抓取艺人公开活动列表

3. 数据处理：
   - 过滤出指定自然年
   - 去重
   - 按稳定字段匹配用户活动与艺人活动
   - 若需要，内部解析艺人名称到对应的艺人页面/艺人 ID
   - 统计活动总数与已出席数

4. 输出结果：
   - 艺人全年活动总数
   - 用户与该艺人相关的出席活动数
   - 出勤率
   - 明细列表（已出席 / 未出席）

5. 展示方式：
   - 静态网页展示
   - 允许用户查看计算结果
   - 红色/绿色等简单方式区分出席和未出席

### 3.2 非功能需求

- 不要求用户登录 Eventernote
- 不依赖自建服务器
- 不需要购买域名
- 抓取频率受控，避免高频访问
- 具有清晰的“手动执行”入口
- 如果抓取失败，输出清晰错误信息
- 艺人名称作为主输入，内部自动适配对应页面/ID，不要求用户手动指定艺人 ID

## 4. 关键设计原则

### 4.1 低频、单次、手动触发

不建议做“网页打开就自动抓取”的模式，原因：

- 会带来不必要的请求频率
- 用户访问很少，自动抓取会造成浪费
- 更难控制 Eventernote 的访问节奏

更合理的方式：

- 在 GitHub Actions 中手动点击运行
- 传入用户 ID、艺人名称和年份
- 系统内部解析对应艺人页面/ID
- 执行一次分析
- 生成结果文件
- 静态网页展示最新结果

### 4.2 仅使用公开数据

目标是分析 Eventernote 的公开页面，不要求用户提供登录态、Cookie、密码等敏感信息。

### 4.3 艺人名称作为第一入口，内部适配对应页面

从需求上调整为：

- 用户不需要手动提供艺人 ID
- 只需要输入艺人名称（例如 `鈴木愛奈`）
- 系统内部通过搜索/解析艺人页面，定位对应的 Eventernote 艺人页面并解析其活动列表

这意味着：

- 输入更简单
- 对普通用户更友好
- 但需要增加内部适配逻辑：广播/搜索/URL 解析、候选艺人匹配、页面跳转和 ID 推断

### 4.4 以稳定字段为主，不以标题模糊匹配为唯一依据

活动匹配重点：

- 优先使用活动 ID / 稳定唯一标识
- 若没有稳定唯一标识，则使用日期 + 标题 + 场地等组合字段
- 若仍无法匹配，标记为“需人工确认”

### 4.5 结果展示要简单且可审计

在展示页面中，应允许用户看到：

- 统计年份
- 该艺人的全年活动总数
- 用户已出席次数
- 出勤率
- 列表明细

这样用户可以自己核对是否符合预期。

## 5. 目标架构

### 5.1 推荐方案：GitHub Pages + GitHub Actions

整体架构：

```text
用户在 GitHub 页面手动触发分析
        ↓
GitHub Actions 运行 Python 脚本
        ↓
脚本接收 用户 ID + 艺人名称 + 年份
        ↓
脚本内部解析艺人名称并定位艺人页面/ID
        ↓
脚本抓取 Eventernote 的公开活动页
        ↓
脚本过滤年份并匹配活动
        ↓
输出 JSON 结果文件
        ↓
GitHub Pages 读取 JSON 并展示静态页面
```

### 5.2 组件说明

1. 前端：静态网页（HTML/CSS/JS）
   - 给用户输入参数
   - 展示结果
   - 读取 `data/latest-result.json`

2. 后端脚本：Python
   - 接收用户 ID + 艺人名称 + 年份
   - 解析艺人名称，定位艺人主页/ID
   - 抓取用户公开活动列表
   - 抓取艺人公开活动列表
   - 解析活动信息
   - 计算活动交集
   - 输出结果 JSON

3. 自动化：GitHub Actions
   - 手动触发 `workflow_dispatch`
   - 配置用户 ID、艺人名称和年份
   - 执行脚本
   - 更新结果文件

4. 托管：GitHub Pages
   - 提供静态页面访问
   - 免服务器和域名

## 6. 技术选型

### 6.1 语言与库

推荐使用：

- Python
- `requests` 或 `httpx`
- `BeautifulSoup` 或 `lxml`
- `pandas`（用于整理统计数据）
- `json` / `csv`（结果保存）

## 7. 抓取与匹配策略

### 7.1 抓取对象

- 用户公开活动列表：`/users/{user_id}/events`
- 艺人公开活动列表：`/actors/{artist_name}/{artist_id}`

### 7.2 艺人名称到页面/ID 的内部解析

由于需求不要求用户手动输入艺人 ID，系统内部需要支持：

1. 使用艺人名称直接访问搜索页或查询页
2. 从搜索结果中匹配到目标艺人的页面
3. 从艺人页面中解析对应的艺人 ID
4. 若解析失败，尝试基于活动页和 URL 结构做候选推断
5. 如果仍无法准确定位，输出 "无法解析艺人页面，请确认艺人名是否正确" 

### 7.3 抓取方式

- 逐页抓取
- 每页请求之间加入延时
- 不使用并发抓取
- 一次最多处理一个用户 + 一个艺人姓名 + 一个年份

### 7.4 匹配原则

优先级：

1. 活动 ID / 稳定唯一标识
2. 日期 + 标题 + 场地组合
3. 若以上都无法稳定匹配，则标记为“需人工确认”

不建议仅使用标题模糊匹配作为唯一依据，因为：

- 标题可能变化
- 多人活动可能混杂
- 单次活动可能在不同页面里字段不一致

### 7.5 统计口径

首版建议采用最简单、最透明的规则：

- 分母：该艺人页面中该自然年发布的独立活动记录数
- 分子：用户活动记录中与该艺人相关并匹配成功的活动数

这样方便审计，也更容易验证功能正确性。

## 9. 频率控制设计

为避免高频抓取，建议：

- 只允许手动触发
- 每次只抓取一个用户/艺人/年份
- 请求之间增加 2~5 秒随机延迟
- 不做自动轮询
- 不做后台定时更新

这非常符合“小团体偶尔查看”的使用场景。

## 11. 预期风险

### 11.1 页面结构变化

Eventernote 页面结构可能变动，导致抓取逻辑失效。

应对方式：

- 优先解析稳定元素
- 把解析逻辑单独封装
- 在出错时输出调试日志

### 11.2 匹配精度

可能存在：

- 某些活动不完全匹配
- 线下与线上活动混合
- 多位艺人同时参加的活动

应对方式：

- 开发“待确认”列表
- 保留原始匹配字段
- 允许人工校验

### 11.3 艺人名称解析失败

用户名或艺人名可能在 Eventernote 中存在中文/日文混合、页面重定向或别名问题。

应对方式：

- 允许输入艺人页面链接作为辅助手段
- 支持模糊匹配与候选列表
- 若无法唯一定位，输出候选结果供用户确认

### 11.4 访问限制

Eventernote 可能对高频访问做限制。

应对方式：

- 手动触发
- 限速
- 最少请求量

这样可以优先验证：

如果第一版通过，再扩展到：

- 支持任意用户 ID
- 支持任意艺人名称
- 支持任意年份
- 支持更丰富的图表和筛选

## 13. 本次需求结论

本项目的核心目标是：

- 在 GitHub 上低成本实现一个小型 Eventernote 出勤率分析工具
- 不需要自建服务器

这个方案落地成本低、风险可控，适合当前场景。
