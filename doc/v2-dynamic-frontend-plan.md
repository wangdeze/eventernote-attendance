# Eventernote 出勤率分析工具 — 架构升级方案（v2：动态网页 + 轻量抓取服务）

## 1. 背景与问题

第一版方案（v1）采用：

```text
GitHub Pages（静态展示）
        +
GitHub Actions（手动 workflow_dispatch 抓取）
        +
仓库内 JSON 结果文件
```

实际使用后暴露的问题：

1. **每次分析都要求用户离开网页，跳转到 Actions 页面手动触发**，交互链路割裂，不符合"打开网页直接看结果"的预期。
2. **必须登录 GitHub 账号、拥有仓库写权限的人才能触发 Actions**，团队内其他人无法自助使用。
3. **结果只能通过提交 commit 的方式写回仓库**，产生大量自动提交历史，且每次分析都在"污染" `main` 分支。
4. **Private 仓库的 Pages 访问会受到 GitHub 账户套餐限制**，出现 404，非付费账户体验非常不稳定。
5. **无法做到"输入信息 → 秒出结果"的即时体验**，实际是"触发任务 → 等待 Actions 跑完 → 手动刷新页面"，级联延迟。
6. 依赖 GitHub Issue/Actions audit 日志作为"运行记录"，对普通使用者并不直观。

## 2. 升级目标

将工具从「静态展示 + CI 手动触发」升级为：

> **动态网页直接驱动一次性抓取与分析，前端提交请求后由轻量后端实时执行，结果直接返回并展示，不再依赖 GitHub Actions 或提交历史。**

具体目标：

- 打开网页，直接填写 `Eventernote 用户 ID` + `艺人名称` + `年份`
- 点击"开始分析"后，前端实时发起一次请求
- 后端（轻量 Serverless 函数）实时执行抓取与匹配
- 结果直接返回给网页展示，无需等待 CI、无需刷新、无需跳转
- 不需要登录 GitHub 账号即可使用（面向小团体内部使用）
- 不产生仓库自动提交
- 仍然保持低频、低成本、无需自建服务器/数据库

## 3. 新架构总览

```text
浏览器（静态网页 UI）
        ↓ 用户填写参数并点击"分析"
        ↓ fetch() 调用
Serverless 函数（Cloudflare Worker）
        ↓ 解析艺人名称 → 定位艺人主页/ID
        ↓ 抓取艺人活动列表（分页）
        ↓ 抓取用户活动列表（分页）
        ↓ 按年份过滤 + 匹配 + 计算出勤率
        ↓ 返回 JSON 响应
浏览器直接渲染结果（表格 + 出勤率 + 明细）
```

### 3.1 为什么选 Cloudflare Worker，而不是继续用 GitHub Actions

| 维度 | GitHub Actions（v1） | Cloudflare Worker（v2） |
|---|---|---|
| 触发方式 | 手动进入 Actions 页面运行 | 网页直接调用，无需跳转 |
| 响应速度 | 分钟级（排队 + 执行 + 提交） | 秒级（同步返回结果） |
| 权限要求 | 需要 GitHub 账号且有仓库权限 | 前端任何人可用（可加简单口令限制） |

## 4. 当前仓库内的 v2 起步实现

为了先启动升级并复用现有 Python 抓取逻辑，仓库内先落地一版“动态前端 + HTTP API”：

1. 根目录继续保留 v1.0 基线，不破坏现有 GitHub Actions 流程
2. 新增 `v2/index.html`，前端直接向分析接口发起 `POST /api/analyze`
3. 新增 `v2/backend/api.py`，把输入校验和统一 JSON 响应封装出来
4. 新增 `v2/backend/server.py`，提供本地和轻量部署都可直接复用的 HTTP 服务入口

这样可以先完成：

- 页面内直接发起分析
- 结果同步返回并渲染
- 后端不再依赖写回 `data/latest-result.json`

后续如果要严格切到 Cloudflare Worker，只需要让 Worker 继续遵守同一个 HTTP/JSON 协议，或作为前置网关转发到该分析接口即可。
